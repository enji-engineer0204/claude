# トライリンクス 社内AI浸透 資料（たたき台 v0.1）

> このドキュメントは「社内にAIを浸透させる」ための**たたき台**です。
> 実際に手を動かしている人（＝作成者）の使い方の特徴を軸に、
> 「AIって結局どう使えばいいの？」に具体例で答えることを狙っています。
> スライド化する前の骨子として、加筆・削除・並べ替え前提で読んでください。

---

## 0. この資料の位置づけ

- **対象**：AIを「まだ触っていない／チャットで質問する程度」の社内メンバー
- **ゴール**：「賢い人だけが使う魔法」ではなく「**面倒ごとを片付ける普通の道具**」として捉え直してもらう
- **やり方**：抽象論ではなく、社内で実際に作ったもの（後述のInstagram追跡ツール）を通して見せる

> ⚠️ たたき台メモ：ここは最終的に「なぜ今、全社でAIなのか（経営的な狙い・生産性・採用/離職・競合）」を
> トライリンクスの言葉で1〜2行入れると刺さります。数字や社内の実感があれば差し込んでください。

---

## 1. 結論：伸びる人のAIの使い方は「6つの型」に集約される

作成者の実際の使い方を分解すると、以下の6つが繰り返し出てきます。
**これはそのまま「社内で真似してほしい型」になります。**

| # | 使い方の型 | ひとことで言うと | ダメな例（ありがち） |
|---|-----------|----------------|--------------------|
| 1 | **相談ではなく「制作」に使う** | 質問して終わりでなく、**動くものを最後まで作らせる** | 「〜のやり方教えて」で満足して自分は動かない |
| 2 | **自分の面倒ごとを自動化する** | 毎回やってる手作業をAIに肩代わりさせる | AIを「すごい検索エンジン」としてしか使わない |
| 3 | **セキュリティ・規約・倫理を最初に織り込む** | 秘密情報の扱い・規約リスク・本人同意を"後回しにしない" | とりあえず動かして情報漏洩・規約違反であとで事故 |
| 4 | **「動いた」で終わらず"運用"まで設計する** | 再起動・自動実行・失敗時の挙動まで考える | 手元で1回動いて満足、翌日には動かない |
| 5 | **既存のツールに繋ぎ込む** | Slack / Discord など**普段見る場所**に結果を流す | 出力がターミナルの中だけで誰も見ない |
| 6 | **他人が使える状態で残す** | READMEとテストを書き、"引き継げる資産"にする | 自分しか使えない・作った本人も1週間後に忘れる |

> 💡 浸透のコツ：この6つは全部「AIが賢いか」ではなく「**頼み方・使い切り方**」の話です。
> つまり才能ではなく"型"なので、真似できる＝教育できる、というのがこの資料のキモです。

## 2. ケーススタディ：Instagram フォロー/フォロワー 差分トラッカー

「6つの型」が全部詰まっている実例。社内デモにそのまま使えます。

### 何を作ったか
- Instagram の **フォロー / フォロワー一覧を定期的に記録**し、前回との**差分**（誰が増えた・減った）を計算
- 変化があった時だけ **Discord / Slack に自動通知**、変化がなければ黙る
- サーバー（クラウド）に置いて**放っておくと勝手に見張り続ける**（Docker常駐）

### 「6つの型」がどう効いているか

**① 制作に使った**
「フォロワーの増減を教えて」で終わらせず、`python -m tracker run` で動く**CLIツール**として完成させた。

**② 面倒ごとの自動化**
手でフォロワー一覧を見比べる作業を丸ごと不要にした。人間は「通知が来た時だけ」見ればいい。

**③ セキュリティ・規約・倫理を先に**
- ログイン情報（`sessionid`）は**パスワード相当の機密**として扱い、Gitにコミットしない設計（`.gitignore`済み・環境変数で渡す）
- READMEの冒頭に**「本人同意のある場合のみ」「規約上グレー」「アクセス頻度に注意」**と明記
- クラウドIPから使うとアカウント制限リスクがある、という**現実の落とし穴まで先回りで警告**

> これは社内展開で一番伝えたい点。**「AIに任せる＝丸投げして事故る」ではなく、
> むしろリスクを最初に言語化してから作る**、という姿勢の見本になります。

**④ 運用まで設計**
- `--dry-run`（送らずに動作確認できる安全弁）
- ループが途中でエラーになっても**止めずに次の間隔で自動リトライ**
- 初回はベースライン作成のみで**誤爆通知しない**
- Docker `restart: unless-stopped` で**サーバー再起動後も自動復帰**、データは永続化

**⑤ 既存ツールに接続**
結果を**Discord / Slack**（＝普段見る場所）に流す。ターミナルに埋もれさせない。

**⑥ 引き継げる状態**
日本語の丁寧なREADME＋`tests/`（テスト）付き。**他の人が読んで使える資産**になっている。

## 3. 明日から真似できる「頼み方テンプレ」

「何をどう頼めばいいか分からない」を潰すための、そのままコピペで使える型。

### テンプレA：面倒ごとを自動化したいとき
```
【やりたいこと】毎回◯◯を手作業でやっていて面倒。これを自動化したい。
【入力】どこから何のデータを取るか（例：スプレッドシート / このメール / このAPI）
【出力】どこに何を出したいか（例：Slackの#◯◯に通知 / CSVで保存）
【制約】これは触っちゃダメ / この情報は秘密 / 実行は1日1回でいい
まず動く最小構成を作って。動いたら運用（自動実行・失敗時の挙動）も相談したい。
```

### テンプレB：まず壁打ち→そのまま制作へ
```
◯◯をやりたいが、やり方が3案くらい思いつく。
それぞれのメリデメを先に整理して。おすすめを1つ選んだら、その場で作り始めて。
```

### テンプレC：レビュー / 引き継ぎ
```
この成果物を、他の人が読んで使える状態にして。
READMEに「これは何か・使い方・注意点（特に機密情報の扱い）」を日本語で。
最低限のテストも付けて。
```

> ⚠️ たたき台メモ：トライリンクスで実際に頻出する"面倒ごと"を2〜3個ヒアリングして、
> ここに**社内の実タスクで書き換えたテンプレ**を入れると一気に自分ごとになります。
> （例：見積書作成、日報集計、問い合わせ一次対応、議事録要約 など）

## 4. 社内浸透ロードマップ（案）

| フェーズ | 目標 | 具体アクション |
|---------|------|--------------|
| **①点火** | 「AIで何ができるか」を体感 | このケーススタディを見せる／各自の"面倒ごと"を1つ書き出す会 |
| **②各自1個** | 全員が自分の面倒ごとを1つ自動化 | テンプレAを配布、詰まったら聞ける相談窓口(Slackチャンネル)を用意 |
| **③共有と型化** | 成功例を横展開 | 作ったものを社内で見せ合う／良かった"頼み方"をこの資料に追記 |
| **④資産化** | 属人化を防ぐ | READMEとテストを付ける文化、秘密情報の扱いルールを社内標準化 |

> 💡 浸透で失敗しがちなのは「①点火」で終わること。**②の"全員が自分の1個を持つ"**まで
> 落とし込めるかが分かれ目です。相談窓口と、小さな成功体験の共有が効きます。

## 5. 想定される社内の不安とその返し（Q&A素案）

| よくある不安 | 返し方 |
|-------------|--------|
| 「情報漏洩が怖い」 | ケーススタディ③の通り、**機密は最初に切り分けるのが正しい使い方**。ルール化すれば逆に安全に前進できる |
| 「エンジニアじゃないと無理では？」 | 6つの型は全部"頼み方"の話。**コードを書くのはAI、人間は"何を・どこまで"を決める** |
| 「一度作っても使い続けられない」 | 型④⑥（運用・引き継ぎ）まで含めて頼めばよい。テンプレCがその型 |
| 「間違った答えを出すのでは？」 | だから`--dry-run`のように**まず試す・検証する一手を挟む**。人間の確認を運用に組み込む |
